SLIDE 4: The Solution: workflow (1:05–2:00)

Follow the question through the diagram. Preparation extracts PDF pages and builds a BM25 keyword index. Ordinary code checks input length and control characters. Next comes an exact-question cache lookup. A matching entry must pass evidence revalidation against the loaded document snapshot before returning. If there is no valid entry, the model planner can search, open a page from a known paper, or answer. Each search returns up to three pages. The planner has four actions and can collect up to twelve pages. It then drafts a structured answer. Think of the planner as a coordinator and the index as the document locator. The dark boxes use the model, and the light boxes use code. This final path uses keyword retrieval. It does not use a vector database or hybrid search.



UNDERSTANDING CHECK: Explain retrieval, model planning, and deterministic checks as separate responsibilities.



SLIDE 5: The Solution: validation (2:00–2:45)

The draft contains claims, source identifiers, and quotations. Code checks that each source was retrieved and that its quotation appears on the cited page after normalizing whitespace. The application supplies the filename and physical page number. A failed draft gets one repair attempt. A second failure withholds the answer. Refusals do not enter the cache. Accepted answers can remain for fifteen minutes, with a maximum of sixty-four entries. This resembles checking a submittal against its reference. Even a quotation copied correctly can be used to support the wrong conclusion. Reviewing the claim and its meaning remains a separate responsibility.

SLIDE 9: Retrieval and Evaluation: performance (5:15–6:10)

The six-question guarded workload took about thirty-one seconds versus twenty-three for baseline. Chat calls rose from seventeen to twenty. Tokens rose from about twenty-eight thousand to forty-five thousand. A0 repeated in roughly eight milliseconds with zero model calls. B0 failed validation, stayed uncached, and repeated the full workflow. For those same two questions, baseline took about eleven seconds and guarded repeats took about fifteen. Fewer calls did not produce an overall speedup. That carries forward another checkpoint lesson: a better summary number does not prove a particular failure was fixed. These timings exclude corpus preparation and include provider variability. Token counts are measured usage, not verified dollar savings. The comparison has to include the failures and cache misses a user actually experiences.

SLIDE 10: Engineering Decisions (6:10–7:15)

Each refinement should address a specific failure and leave a record of what changed. I kept BM25 keyword retrieval and the existing agent so I could evaluate guards and caching against that baseline. This does not establish that BM25 beats vector or hybrid retrieval. Those alternatives need a separate comparison using the same corpus and questions. Second, checking retrieved source identifiers and quotations gives me rules I can inspect without another model judge. A judge might assess meaning more flexibly, but adds calls and its own errors. Strict quotation matching also has a cost: it rejected the useful B0 comparison. Third, an exact-question cache avoids uncertainty about whether two questions mean the same thing. A valid hit needs no model call, but paraphrases miss the cache. I kept prompts, JSON results, review notes, and call records so these decisions can be checked against what actually happened.
